<objective>
Build the Workflow Engine — the keystone of Phase 2. A durable Inngest function executes multi-step runs with per-step checkpointing, branching for L1 (manual hold) / L2 (pause → approval → resume) / L3 (autonomous), and writes an idempotent Activity entry for every action. The L2 pause/resume via `step.waitForEvent` is Success Criterion #5 and the single highest-risk component. This plan also closes the observability loop left open in 02-03: it wires `writeActivity()` into the Shopify `mutations.ts` call-site that 02-03 left as a documented TODO, so every external write emits a structured Activity event BEFORE the Shopify API call (CLAUDE.md observability constraint).

Purpose: This is the "have it run successfully" leg of the journey. RESEARCH critical signal #1: the CEL `if` uses `async` for the matched (awaited) event — inverting `async`/`event` is a silent wrong-resume bug. This plan gets its own focus and the two hardest Wave-0 tests.
Output: executeWorkflowRun, activity + approvals helpers, the wired-up mutations observability call-site, approval Server Actions, inline approval card, and the keystone tests green.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Server Action → Inngest resume | approval.resolved event triggers a privileged external write |
| Inngest event → run execution | a forged event must not cause an unauthorized action |
| run retry → external effect | retries must not double-write or duplicate Activity |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-07-01 | Tampering | wrong-approval resume (CEL inversion) | mitigate | `if: async.data.approvalId == <id>` matches only the specific approval; verified by the two-concurrent-run test (Pitfall 1) |
| T-2-07-02 | Elevation | forged approval.resolved event | mitigate | Engine re-looks-up the approval by id + user ownership before executing; the event alone never bypasses DB auth |
| T-2-07-03 | Tampering | duplicate external write on retry | mitigate | Idempotent mutations (02-03) + writeActivity ON CONFLICT DO NOTHING on (workflow_run_id, step_id) |
| T-2-07-04 | Information Disclosure | cross-user approval/run access | mitigate | serviceDb queries filtered by user_id; approvals/runs RLS-enabled; Realtime channel `{ private:true }` (Pitfall 5) |
| T-2-07-05 | Repudiation | unlogged agent action | mitigate | writeActivity before every external effect (WF-06) gives an auditable trail; Shopify mutations call-site wired in Task 1 |
</threat_model>
