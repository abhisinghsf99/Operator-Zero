## Phase Goal

**As a** new Operator Zero user, **I want to** sign up (email/password or Google) and reach a private home page that already knows who I am, **so that** the whole authenticated app rail — login to session to guarded route to my own database row — is proven working end to end.

<objective>
Build the auth + walking-skeleton vertical slice that ties together the scaffold (Plan 01) and the schema (Plan 02): email/password signup + login via @supabase/ssr Server Actions, "Sign in with Google" OAuth with a server-side callback code exchange, root middleware that guards /app/* with getClaims() and refreshes the httpOnly session cookie, and a guarded /app/home Server Component that performs ONE real RLS-enforced Drizzle round-trip against the signed-in user's user_profiles row (create-on-first-visit, read-thereafter).

This is the thinnest end-to-end slice that proves every web-tier rail Phase 2 builds on: signup/login UI -> Server Action -> Supabase Auth -> session middleware -> guarded RSC -> Drizzle/RLS read+write. After this plan a real person can do something they could not before: sign up and reach a private page that reads their own row from the live database.

Purpose: AUTH-01 (email/password signup + login), AUTH-02 (Google OAuth), AUTH-03 (httpOnly cookie session with 30-day rolling refresh + middleware guard on /app/*).
Output: Supabase server/browser clients, signup/login routes + Server Actions, OAuth callback Route Handler, root middleware, guarded app shell + home page with a live user_profiles round-trip, plus the Playwright happy-path e2e and a middleware unit test.
</objective>

<deviation_notes>
- Server-side session reads use supabase.auth.getClaims() everywhere (middleware, profile helper) — NEVER getSession() (RESEARCH.md Pitfall 1 / finding #1). claims.sub is the user_id.
- The user_profiles round-trip uses the RLS-enforced db client from Plan 02, NOT serviceDb. The user JWT (carried in the cookie and forwarded by @supabase/ssr) is what RLS authorizes against. The agent-tier serviceDb is out of scope here.
- 30-day rolling refresh is a Supabase project setting (JWT/refresh-token expiry), not app code; @supabase/ssr's setAll in middleware performs the per-request rolling refresh. Plan 01 provisioned the project; this plan relies on Supabase defaults for the 30-day window.
- The OAuth callback next redirect param MUST be validated as a relative same-origin path (reject absolute URLs and protocol-relative // values) to close the open-redirect hole; default to /app/home.
</deviation_notes>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> middleware/Route Handlers | Untrusted requests (cookies, OAuth callback params) cross into server auth code |
| browser -> Supabase Auth | Credentials + OAuth code flow; identity established here, carried by an httpOnly cookie |
| web tier (user JWT) -> Postgres | The /app/home query must only touch the caller's user_profiles row (RLS) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-04-01 | Spoofing | Server-side session validation (middleware + profile helper) | mitigate | Use supabase.auth.getClaims() (validates JWT signature) everywhere; getSession() is forbidden — Task 2 verify greps for its absence; Task 3 unit-tests the no-claims redirect |
| T-1-04-02 | Elevation of Privilege | middleware bypass to /app/* | mitigate | Root middleware matcher covers all non-static paths; unauthenticated /app/* -> 307 /login; defense-in-depth via Plan 02 RLS so even a bypassed route cannot read another user's row; Task 3 asserts the redirect |
| T-1-04-03 | Tampering | OAuth state / CSRF on the callback | mitigate | Supabase PKCE flow generates + verifies the state parameter; exchangeCodeForSession performs the PKCE exchange server-side in app/auth/callback/route.ts — no hand-rolled state handling |
| T-1-04-04 | Spoofing | Open redirect via callback next param | mitigate | next is validated as a same-origin relative path (reject absolute + protocol-relative //), default /app/home; Task 4 probes next=absolute and confirms no off-site navigation |
| T-1-04-05 | Info Disclosure | Session cookie flags | mitigate | @supabase/ssr sets the auth cookie httpOnly + sameSite + secure (secure on deployed origin); cookies are written only by middleware/Route Handlers, never client JS; Task 4 inspects the cookie flags |
| T-1-04-06 | Info Disclosure | Service-role key / over-privileged DB access in the web tier | mitigate | /app/home uses the RLS-enforced db client only; serviceDb is never imported here; no NEXT_PUBLIC_ prefix on SUPABASE_SERVICE_ROLE_KEY (Task 2 acceptance) |
| T-1-04-07 | Elevation of Privilege | Cross-user user_profiles read/write | mitigate | getOrCreateProfile keys strictly on claims.sub and queries via the RLS db client; RLS policy (SELECT auth.uid()) = user_id from Plan 02 is the safety net |
</threat_model>
