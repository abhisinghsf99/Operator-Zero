<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| web tier (user JWT) -> Postgres | Authenticated queries must only see the caller's rows |
| agent tier (service role) -> Postgres | Service role bypasses RLS; code is the only filter |
| app memory -> integrations table | OAuth tokens cross from plaintext (memory) to ciphertext (DB) here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-02-01 | Elevation of Privilege | Cross-user row access | mitigate | RLS policy `(SELECT auth.uid()) = user_id` on both tables (Task 2/3); verified live in Task 4; defense-in-depth via explicit user_id filters in every query |
| T-1-02-02 | Info Disclosure | OAuth token at rest | mitigate | libsodium secretbox in lib/integrations/crypto.ts (Task 1); access_token_encrypted is notNull ciphertext; plaintext never written; crypto test asserts ciphertext != plaintext |
| T-1-02-03 | Info Disclosure | Service-role key / RLS bypass | mitigate | SUPABASE_SERVICE_ROLE_KEY is server-only (no NEXT_PUBLIC_); serviceDb confined to lib/db/client.ts; Task 4 documents that agent-tier code MUST filter by user_id |
| T-1-02-04 | Tampering | ENCRYPTION_KEY management | mitigate | Key from env (Supabase secret + Vercel env); crypto helper throws on missing/wrong-length key; key never committed (.env.local gitignored) |
| T-1-02-05 | Tampering | Migration desync (Drizzle vs Supabase) | mitigate | Generate-then-copy-then-push workflow only; never drizzle-kit migrate (Task 3 acceptance forbids it) |
</threat_model>
